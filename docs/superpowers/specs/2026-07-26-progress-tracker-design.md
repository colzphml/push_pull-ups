# Запись прогрессии на сайте — дизайн

**Дата:** 2026-07-26
**Автор:** Claude + colz
**Статус:** на вычитку

---

## 1. Контекст и проблема

Сайт `push_pull-ups` — статика на GitHub Pages с PWA. Недели генерируются скиллом
`/make-week`, план пишется в `history/training.db` (таблица `exercise_log`).

**Проблема:** в `exercise_log` 267 строк плана и **ни одной заполненной `done`**.
План записывается, факт — нет. Сейчас факт живёт только в чате: colz устно
пересказывает прошлую неделю при генерации следующей. Это значит:

- нет объективной истории выполнения — только память и ощущение;
- метрика недели 9 («попадаемость 5 из 7») не измеряется, а оценивается на глаз;
- `training_rules` пополняются только тем, что colz вспомнил и проговорил;
- при генерации недели я опираюсь на пересказ, а не на данные.

**Задача:** дать возможность отмечать выполнение прямо на странице недели, с
телефона и с компьютера, так чтобы факт автоматически доезжал до репозитория и
был виден скиллу `/make-week` без ручных действий.

## 2. Цели и не-цели

**Цели:**
- Отметка выполнения в один тап с карточки недели.
- Опционально — фактические цифры, ощущения и заметка.
- Работа офлайн: отметка не должна ждать сети.
- Синхронизация телефон ↔ компьютер.
- Автоматическая доставка факта в репозиторий → в `exercise_log`.
- Счётчик попадаемости на виду.

**Не-цели (сознательно вне этого захода):**
- Графики и визуализация прогрессии — рисовать не по чему, данных пока нет.
  Вернуться через 3–4 недели накопления.
- Запись рекордов в таблицу `progress` (max_hang_sec и прочие) — отдельная фича
  со своим UI.
- Авторизация, мультипользовательность — проект на одного человека.
- Ретроспективное заполнение прошедших недель.

## 3. Ключевые решения и обоснования

### 3.1 Хранилище — git-репозиторий, без внешних сервисов

Объём данных: ~30 строк в неделю, ~1500 в год. Для такого объёма настоящая БД
избыточна; реальная задача — не «где хранить», а «как доставить с телефона в репо».

Рассмотренные альтернативы:

| Вариант | Почему отклонён |
|---|---|
| Supabase / Firebase | Free-тариф Supabase паузит проект после ~недели простоя (у colz бывают отпуска на две недели). Anon-ключ публичен → обязателен RLS. Появляется второй источник правды рядом с `training.db`. |
| Cloudflare Worker + D1 | Токен жил бы на сервере (плюс), но добавляет аккаунт, `wrangler` и отдельный деплой ради одного пользователя. |
| Lovable / v0 / bolt.new | Это генераторы приложений, а не хранилища. Построили бы отдельное React-приложение на Supabase — четвёртый артефакт вне цикла `/make-week`, без текущей темы и PWA. |
| Только localStorage | Не решает синхронизацию телефон ↔ компьютер и не доставляет факт в репозиторий. |

**Выбрано:** сайт пишет напрямую в GitHub через Contents API с fine-grained
токеном. Ноль сервисов, ноль регистраций, ноль расходов, ничего не засыпает.
Данные версионируются в git и бэкапятся в каждом клоне.

### 3.2 Запись мгновенная и локальная, отправка отложенная

Тап пишет в `localStorage` немедленно и работает всегда — офлайн, в метро, при
недоступном GitHub. Отправка в репозиторий идёт фоном при наличии сети и
повторяется при следующем открытии, если не прошла. Пользователь никогда не ждёт
сеть, чтобы отметить подход.

### 3.3 Один общий файл кода, а не копия в каждой неделе

Каждая неделя — отдельный HTML на ~600 строк. Логика логирования вписанная в
каждый файл распухнет и разъедется по версиям. Код живёт в `assets/tracker.js`,
подключается строкой из каждой недели, правится в одном месте.

## 4. Архитектура

```
[карточка в week_*.html]  --тап по кружку-->  [localStorage: очередь]
                                                      |
                                          (дебаунс 2 мин / кнопка «синк»)
                                                      v
                                            [GitHub Contents API]
                                                      v
                                     history/log/2026-07-27.json  (в репо)
                                                      v
                                            /make-week читает JSON
                                                      v
                                   заливает факт в exercise_log (SQLite)
```

### Новые артефакты

**`assets/tracker.js`** — вся логика одним файлом:
- рендер контролов поверх существующих карточек;
- локальное хранилище и очередь неотправленного;
- синхронизация с GitHub Contents API;
- экран настроек (ввод токена, статус синхронизации).

**`history/log/YYYY-MM-DD.json`** — по файлу на неделю, имя = дата начала недели.

**Разметка недель не меняется.** Всё нужное для связи со строкой `exercise_log`
уже есть в существующих классах: дата — `.day-col[data-date]`, блок — класс
`dot-*` на точке, упражнение — `.meal-title`, план — `.meal-kcal`, окно — текст
`.meal-type` до разделителя. Дополнительные `data-*` атрибуты не нужны, и прошлые
недели становятся отслеживаемыми добавлением одной строки `<script>`.

## 5. Формат данных

```json
{
  "week_start": "2026-07-27",
  "entries": [
    {
      "date": "2026-07-27",
      "window": "утро",
      "block": "pull",
      "exercise": "вис на перекладине",
      "planned": "3×20-25 сек",
      "done": 1,
      "actual": "3×20 сек",
      "felt": "норм",
      "note": "",
      "updated_at": "2026-07-27T08:14:00Z",
      "device": "phone"
    }
  ]
}
```

- **Ключ записи:** `date + block + exercise`.
- Поля один в один с колонками `exercise_log`, чтобы заливка в SQLite была
  тривиальным UPDATE по ключу.
- `done`: `1` сделал, `0` не вышло, отсутствие записи = нет отметки.
- `felt`: одно из `легко` / `норм` / `тяжело` / `больно`.
- `device` — для разбора конфликтов при отладке.

### Требуемая миграция схемы

В `exercise_log` **нет колонки под фактическое выполнение** — есть `planned`, но
некуда положить `actual`. Класть факт в `note` неправильно: заметка это
свободный комментарий, а факт нужен для сравнения с планом. Требуется:

```sql
ALTER TABLE exercise_log ADD COLUMN actual TEXT;
```

Соответствующая правка в `history/schema.sql`.

**Замечание для реализации:** колонка `window` — зарезервированное слово SQLite
(оконные функции). В запросах экранировать: `"window"`.

### Разрешение конфликтов

Конфликт решается на уровне записи, а не файла:

1. Перед записью читаем актуальный файл с его SHA.
2. Вливаем свои изменения в прочитанное содержимое.
3. Отправляем PUT с этим SHA.
4. Если GitHub отвечает 409 (SHA устарел — кто-то записал раньше) — перечитываем
   и повторяем, максимум 3 попытки.

Внутри файла при слиянии двух версий одной записи побеждает бо́льший `updated_at`.
Галочка с телефона не затрёт заметку, поставленную с ноутбука десятью минутами
позже.

## 6. Интерфейс

### Карточка

```
┌─────────────────────────────────┐
│ ● Утро · Подтягивания      ( ) │ ← кружок: тап = отметка
│                                 │   (не переворачивает карточку)
│ Вис на перекладине              │
│ 3 × 20-25 сек                   │
│                        ↻ детали │
└─────────────────────────────────┘

после отметки:
┌─────────────────────────────────┐
│ ● Утро · Подтягивания      (✓) │
│ Вис на перекладине              │
│ 3 × 20-25 сек                   │
│           ✎ уточнить   ↻ детали │ ← появилось только сейчас
└─────────────────────────────────┘
```

Существующая карточка уже кликабельна — тап переворачивает её на оборот с
техникой. Поэтому отметка вынесена в отдельный элемент в углу, а его обработчик
останавливает всплытие события.

**Кружок циклический:** пусто → ✓ сделал → ✕ не вышло → пусто.
«Не вышло» — тоже данные: они отличают осознанный пропуск от забывчивости.

### Шторка «уточнить»

Появляется только после отметки — прогрессивное раскрытие, чистый интерфейс до
первого касания.

- **Как вышло** — одно текстовое поле, **предзаполненное планом**. Всё по плану →
  просто закрыть, ничего не печатая. Не по плану → поправить на `2×18 сек`.
  Единое свободное поле, а не структурированные подходы, потому что в одном
  списке соседствуют минуты йоги, секунды виса, повторы отжиманий и секунды
  холодной воды — общая форма для них невозможна.
- **Ощущения** — четыре чипа в один тап: `легко · норм · тяжело · больно`.
  «Больно» подсвечивается красным.
- **Заметка** — необязательное текстовое поле.

### Шапка недели

- **Счётчик попадаемости:** `Попал: 4 из 7 дней` — метрика, на которую colz сейчас
  играет, должна быть видна без листания.
- **Индикатор синхронизации:** зелёная точка «всё в репо», жёлтая «3 ждут
  отправки», красная «нужен токен». Тап открывает настройки.

Прошедшие неотмеченные карточки визуально гаснут, но в данных остаются «нет
отметки» — молчание не выдаётся за пропуск, это разные вещи.

## 7. Токен и безопасность

**Тип:** fine-grained PAT, выпускается вручную на github.com (API создания
токенов не существует принципиально).

**Область действия:**
- Repository access: `Only select repositories` → `colzphml/push_pull-ups`
- Repository permissions: **`Contents: Read and write`**, и только это
  (`Metadata: Read-only` подставляется автоматически как обязательная зависимость)

**Хранение:** `localStorage` на каждом устройстве, вводится вручную. В git не
попадает никогда.

**Принятый риск:** при краже разблокированного устройства вор получает право
записи в один репозиторий с историей тренировок. Не в почту, не в другие
репозитории. Всё версионируется в git и откатывается одной командой. Токен
отзывается одной кнопкой. Это приемлемая цена за отсутствие серверной части.

**Экранирование:** заметки пользователя рендерятся через `textContent`, не через
`innerHTML` — иначе кавычка в заметке ломает вёрстку.

### Особенности хранилища на устройствах

Safari на iOS удаляет `localStorage` у сайтов, не открывавшихся 7 дней (ITP). При
отпуске длиннее недели токен придётся ввести заново — данные при этом не теряются,
они уже в репозитории. На сайты, добавленные на домашний экран как standalone-PWA,
это правило не распространяется. На Android ограничения нет.

## 8. Частота коммитов

Отправка с дебаунсом 2 минуты после последней отметки — утренние три галочки
схлопываются в один коммит. Ожидаемо 2–4 коммита в день, ~20 за неделю, сообщение
вида `log: 2026-07-27 (4 записи)`.

Это заметный шум в истории репозитория — осознанная плата за отсутствие сервера.
Взамен получается бесплатный аудит-лог с временем каждой отметки.

## 9. Подводный камень в `sw.js`

Текущий service worker кэширует **любой** GET-ответ, включая запросы к
`api.github.com`. Без изменений чтение файла вернётся из кэша со старым SHA, и
синхронизация уйдёт в бесконечный конфликт.

Требуется:
- явно исключить внешние домены (всё, кроме своего origin) из кэширования;
- добавить `assets/tracker.js` в список `ASSETS`;
- поднять версию кэша до `pushpull-v2`.

## 10. Изменения в скилле `/make-week`

1. **Читать** `history/log/*.json` за прошедшую неделю перед генерацией новой.
2. **Заливать** факт в `exercise_log` — UPDATE по ключу `date + block + exercise`,
   поля `done`, `actual`, `felt`, `note`.
3. **Генерировать** новые недели с подключением `assets/tracker.js` перед `</body>`.
4. **Предлагать** упражнения с отметкой `больно` в `training_rules` с рейтингом −2
   (предлагать, а не проставлять молча — решение за colz).

## 11. Порядок внедрения

1. Миграция схемы: `ALTER TABLE exercise_log ADD COLUMN actual TEXT`.
2. `assets/tracker.js` + правки `sw.js`.
3. Ручное подключение к текущей неделе `week_2026-07-27.html` — чтобы начать
   отмечать сразу, а не с 3 августа.
4. Выпуск токена и проверка полного цикла: отметка на телефоне → файл в репо.
5. Обновление скилла `/make-week`.
6. Обновление `CLAUDE.md`: описание трекера и формата `history/log/`.

## 12. Проверка работоспособности

- Отметка в режиме «в самолёте» сохраняется и уезжает после включения сети.
- Отметка с телефона и заметка с компьютера по одной карточке не затирают друг
  друга.
- Переворот карточки на оборот с техникой продолжает работать, тап по кружку его
  не вызывает.
- Повторное открытие страницы показывает ранее поставленные отметки.
- Без токена сайт работает как раньше и показывает красную точку, а не ошибку.
